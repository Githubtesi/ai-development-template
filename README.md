# AI Development Template

AI（ChatGPT、Cursor、その他のAIコーディングツール）を利用したソフトウェア開発のためのテンプレートです。

このテンプレートでは、**コードだけでなく、仕様・設計・タスク・AIルール・判断履歴をGitで管理する**ことを目的とします。

---

# 1. 基本的な考え方

AIにコードを直接書かせるのではなく、

```text
人間
 ↓
要求・仕様
 ↓
タスク
 ↓
AIによる分析
 ↓
修正案
 ↓
人間による確認
 ↓
AIによる実装
 ↓
テスト
 ↓
Gitで記録
```

という流れで開発します。

AIが判断に迷った場合は、勝手に仕様を変更せず、人間に確認します。

# 2. ディレクトリ構成

```text
project/
│
├─ .ai/
│   ├─ rules.md
│   ├─ project_map.md
│   ├─ current_task.md
│   ├─ decisions.md
│   └─ AI_WORKFLOW.md
│
├─ docs/
│   ├─ requirements.md
│   ├─ architecture.md
│   └─ glossary.md
│
├─ task/
│   ├─ TODO.md
│   └─ TASK_TEMPLATE.md
│
├─ src/
│
├─ tests/
│
├─ README.md
├─ CHANGELOG.md
└─ .gitignore
```

## `.ai/`

AIがプロジェクトを理解するための情報を保存します。

| ファイル              | 役割           |
| ----------------- | ------------ |
| `rules.md`        | AIが守る開発ルール   |
| `project_map.md`  | プロジェクト全体の構造  |
| `current_task.md` | 現在取り組んでいるタスク |
| `decisions.md`    | 設計上の重要な判断    |
| `AI_WORKFLOW.md`  | AIを利用した開発手順  |

## `docs/`

人間とAIが共有するプロジェクト仕様を保存します。

## `task/`

AIや人間が実施する作業を管理します。

# 3. プロジェクト開始時

テンプレートから新しいGitHubリポジトリを作成します。

その後、以下のファイルをプロジェクトに合わせて更新します。

```text
README.md
docs/requirements.md
docs/architecture.md
docs/glossary.md
.ai/project_map.md
.ai/current_task.md
```

特に、

```text
docs/requirements.md
```

には、

* 何を作るのか
* なぜ作るのか
* 入力
* 出力
* 基本的な処理
* 制約事項

を記載します。

# 4. ChatGPTとGitHubの連携

このテンプレートでは、GitHubをプロジェクトの正本（Source of Truth）として使用します。

ChatGPTをGitHubと連携することで、GitHub上に保存されたソースコード、仕様書、AIルール、設計資料などをChatGPTから検索・確認し、プロジェクトの開発支援に利用できます。

## 4.1 GitHubを正本とする理由

AIを利用した開発では、AIが現在のプロジェクトの状態を正しく理解していることが重要です。

そのため、以下の情報をローカルPCだけに保存するのではなく、GitHubで管理します。

```text
.ai/
├─ rules.md
├─ project_map.md
├─ current_task.md
├─ decisions.md
└─ AI_WORKFLOW.md

docs/
├─ requirements.md
├─ architecture.md
└─ glossary.md

src/
tests/
README.md
CHANGELOG.md
```

GitHubをプロジェクトの正本とすることで、人間とAIが同じプロジェクト情報を参照できる状態を作ります。

## 4.2 ChatGPTとGitHubを接続する

ChatGPTからGitHub上のプロジェクトを確認する場合は、ChatGPTの設定からGitHubを接続します。

基本的な流れは以下です。

```text
ChatGPT
   ↓
設定
   ↓
アプリ
   ↓
GitHub
   ↓
GitHubアカウントを認証
   ↓
アクセスするリポジトリを許可
```

GitHubとの接続方法や画面は、ChatGPTおよびGitHubの仕様変更によって変わる場合があります。

実際の接続時は、現在表示されている設定画面に従ってください。

## 4.3 接続後の使い方

GitHubとの接続が完了したら、ChatGPTに対象となるリポジトリを指定してプロジェクトの確認を依頼します。

例えば、プロジェクト開始時には以下のように指示します。

```text
GitHubのこのプロジェクトを確認してください。

まずコードの変更は行わないでください。

以下のファイルを確認してください。

.ai/rules.md
.ai/project_map.md
.ai/current_task.md
.ai/decisions.md
.ai/AI_WORKFLOW.md

docs/requirements.md
docs/architecture.md
docs/glossary.md

README.md

これらをプロジェクトの正式な情報として扱ってください。

そのうえで、

1. プロジェクトの目的
2. ディレクトリ構成
3. 開発ルール
4. 現在のタスク
5. アーキテクチャ
6. 重要な設計判断

を整理してください。

まだコードは変更しないでください。
```

## 4.4 ソースコードを確認してもらう

プロジェクトの理解ができたら、具体的なタスクに関係するソースコードを調査させます。

例えば、

```text
TASK-001に関係するソースコードを調査してください。

まだコードは変更しないでください。

以下について説明してください。

1. 関係するファイル
2. 各ファイルの役割
3. 処理の流れ
4. 現在の実装
5. 問題が発生している箇所
6. 問題の原因
7. 他の機能への影響
```

というように依頼します。

AIには、最初からプロジェクト全体を変更させるのではなく、

```text
プロジェクト理解
      ↓
関連コードの調査
      ↓
原因分析
      ↓
修正案
      ↓
人間による確認
      ↓
実装
```

という順番で作業させます。

## 4.5 ChatGPTとCursor / PyCharmの役割

GitHubを中心として、各ツールの役割を分けます。

| ツール              | 主な役割                |
| ---------------- | ------------------- |
| GitHub           | ソースコード・仕様・ルール・履歴の管理 |
| ChatGPT          | プロジェクト調査・分析・設計・レビュー |
| Cursor / PyCharm | ローカルコードの編集・実装・テスト   |
| Git              | 変更履歴の管理             |

基本的な流れは以下です。

```text
                    GitHub
                 （プロジェクトの正本）
                       ↑
                       │
          ┌────────────┴────────────┐
          │                         │
       ChatGPT                 Cursor / PyCharm
     調査・分析・設計             実装・テスト
          │                         │
          └────────────┬────────────┘
                       ↓
                  Git commit
                       ↓
                    GitHub
```

ChatGPTではプロジェクト全体の理解、調査、設計、レビューを行い、Cursor / PyCharmでは実際のコード編集やローカル環境でのテストを行います。

## 4.6 GitHub上の情報を常に最新にする

ChatGPTに正しい情報を確認させるため、重要な変更を行った場合はGitHubへ反映します。

例えば、

```text
コードを変更
    ↓
テスト
    ↓
ドキュメント更新
    ↓
Git commit
    ↓
GitHubへpush
```

という流れを基本とします。

特に以下の情報が変更された場合は、GitHub上のファイルも更新します。

* プロジェクト構成
* 要件
* アーキテクチャ
* AIルール
* 設計判断
* 現在のタスク
* テスト方法

これにより、次回ChatGPTを使用するときも、現在のプロジェクト情報を確認しやすくなります。

> **重要：GitHubに存在しない情報をChatGPTが必ず把握しているとは限りません。**
>
> 重要な仕様・ルール・設計判断は、可能な限りプロジェクトのドキュメントとしてGitHubに記録してください。


## STEP 1：プロジェクトを理解させる

まず、ChatGPTにプロジェクトのルールと仕様を確認させます。

例：

```text
GitHubのこのプロジェクトを確認してください。

まずコードの変更は行わないでください。

以下を確認してください。

.ai/rules.md
.ai/project_map.md
docs/requirements.md
docs/architecture.md
docs/glossary.md
.ai/current_task.md

その後、プロジェクトの目的、構造、現在の状態を整理してください。

まだコードの修正は行わないでください。
```

---

# 5. STEP 2：関連するコードを調査する

次に、現在のタスクに関係するコードを調査します。

例：

```text
現在のTASK-001に関係するコードを特定してください。

まだコードを変更しないでください。

以下について説明してください。

1. 関係するファイル
2. 各ファイルの役割
3. 処理の流れ
4. 現在の問題
5. 問題が発生している原因
6. 他の機能への影響
```

AIには、**必要なファイルを特定してから分析させる**ことを推奨します。

---

# 6. STEP 3：修正方法を検討する

原因が分かったら、修正方法を検討します。

例：

```text
原因の分析結果をもとに、修正方法を提案してください。

まだコードは変更しないでください。

以下を含めてください。

1. 修正方針
2. 修正対象ファイル
3. 変更する処理
4. 変更しない処理
5. 想定される影響
6. テスト方法
7. リスク
```

---

# 7. STEP 4：人間が確認する

AIの提案を人間が確認します。

問題がなければ、

```text
提案内容で実装してください。
```

と指示します。

問題がある場合は、

```text
この部分は仕様と異なります。

○○ではなく、△△にしてください。

その他の提案内容は変更しません。
```

のように修正します。

---

# 8. STEP 5：実装

実装を依頼するときは、変更範囲を明確にします。

例：

```text
先ほどの修正方針で実装してください。

変更対象：
- src/ocr/company_detector.py
- tests/test_company_detector.py

変更対象外：
- src/main.py
- src/database/
- ファイル移動処理

実装後に以下を確認してください。

1. 構文エラーがないこと
2. 既存テストが成功すること
3. 新しい処理のテストが成功すること
4. 既存仕様を変更していないこと
```

AIに「プロジェクト全体をきれいにしてください」のような曖昧な依頼をせず、**変更範囲を限定する**ことを推奨します。

---

# 9. STEP 6：テスト

実装後は必ずテストします。

例：

```text
今回の変更についてテストしてください。

以下を確認してください。

- 新機能
- 変更した機能
- 関連する既存機能
- エラーケース
- 境界値

テスト結果と、失敗した場合の原因を説明してください。
```

テストが失敗した場合は、原因を確認してから追加修正を行います。

---

# 10. STEP 7：ドキュメントを更新する

実装が完了したら、必要に応じて以下を更新します。

```text
.ai/project_map.md
.ai/current_task.md
.ai/decisions.md
docs/requirements.md
docs/architecture.md
CHANGELOG.md
task/TODO.md
```

特に、設計上の重要な判断があった場合は、

```text
.ai/decisions.md
```

に記録します。

---

# 11. STEP 8：Gitに記録する

変更内容を確認してGitにコミットします。

例：

```bash
git status
git diff
git add .
git commit -m "feat: add company detection"
git push
```

コミット前に、変更内容が意図したものだけになっていることを確認してください。

# 12. ChatGPTに依頼するときの基本ルール

以下のような順番で依頼します。

```text
① 理解
↓
② 調査
↓
③ 原因分析
↓
④ 修正案
↓
⑤ 人間確認
↓
⑥ 実装
↓
⑦ テスト
↓
⑧ ドキュメント更新
↓
⑨ Git記録
```

原則として、**①～④を確認せずに⑥の実装へ進まない**ようにします。

# 13. ChatGPTに渡す基本プロンプト

プロジェクト開始時には、以下をベースに使用できます。

```text
このGitHubプロジェクトを開発支援してください。

まず以下を確認してください。

1. .ai/rules.md
2. .ai/project_map.md
3. .ai/current_task.md
4. docs/requirements.md
5. docs/architecture.md
6. docs/glossary.md

これらをプロジェクトの正式な情報として扱ってください。

不明な仕様は推測せず、確認してください。

コードを変更する場合は、最初に

1. 現状
2. 原因
3. 修正対象
4. 修正方法
5. 影響範囲
6. テスト方法

を説明してください。

人間が実装を承認するまではコードを変更しないでください。
```

# 14. AIルールの改善

このテンプレートのルールは固定されたものではありません。

開発中に問題が発生した場合、

```text
問題発生
 ↓
原因を確認
 ↓
今後も同じ問題が起こる可能性があるか？
 ↓ YES
AIルールを改善
 ↓
CHANGELOG.mdに記録
```

という流れでルールを改善します。

例：

```text
AIが既存関数を不要と判断して削除した
```

↓

`rules.md` に、

```text
既存関数を削除する場合は、
削除理由と影響範囲を説明し、
人間の承認を得る。
```

を追加します。

これによって、このテンプレート自体が開発経験を蓄積していきます。

# 15. AIと人間の役割

このテンプレートでは、AIと人間の役割を以下のように考えます。

### 人間

* 目的を決める
* 仕様を決める
* AIの提案を確認する
* 重要な設計を決定する
* 最終的な変更を承認する

### AI

* コードを読む
* プロジェクト構造を分析する
* 問題の原因を調査する
* 修正方法を提案する
* コードを実装する
* テストを作成する
* ドキュメント作成を支援する

AIは仕様を勝手に決定せず、**人間が決めた仕様を実装する開発支援者として使用します。**

# 18. 最終的な目標

このテンプレートの目的は、

> **AIがプロジェクトを理解し、人間と同じルール・仕様を基準に開発できる環境を作ること**

です。

コードだけを管理するのではなく、

```text
仕様
設計
ルール
判断
タスク
コード
テスト
変更履歴
```

を一つのプロジェクトとして管理します。

AIを変更しても、プロジェクトに蓄積された情報を引き継げる状態を目指します。
